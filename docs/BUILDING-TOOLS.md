# Building a tool (guide for AI coding tools and contributors)

Read this whole file before writing any code. It tells you exactly where a new
calculator goes, which files you may change, and what you must hand back.

**The one rule that matters most:** you change files **only inside your own tool
folder**, `sites/home-project-calcs/tools/<tool-slug>/`. Everything else in the
repo is shared and off-limits.

---

## 2. Your tool folder and what each file is for

`sites/home-project-calcs/tools/<tool-slug>/`

| File | Required | What it is for |
|---|---|---|
| `logic.js` | yes | **Pure** calculation code. Exports `calculate(raw)`. No DOM, no `window`/`document`, no network, no storage. Validates inputs and returns results or clear error messages. |
| `logic.test.js` | yes | Vitest tests for `logic.js`: at least 3 known-answer cases plus edge cases (section 8). Keep the "scaffold guard" block at the bottom. |
| `ui.js` | yes | Connects the shared form and results area to `logic.js` with `bindCalculator`. Usually unchanged from the template. No business logic. |
| `meta.json` | yes | Title, benefit, meta description, keywords, category, intro, last-updated date, layout, chart style, the form's **inputs** and **outputs**, related tools, and dated **sources**. |
| `page.md` | yes | The page copy below the calculator (section 6). Markdown, H2 sections. |
| `tool.css` | yes (may be empty) | This tool's look: theme token overrides and small layout touches, all scoped to `[data-tool="<tool-slug>"]` (section 7). |
| `assets/hero.svg` (or `.png/.jpg/.webp/.avif`) | optional | A small illustration shown next to the H1. Under 100 KB. Delete the template's `hero.svg` if you don't want one. |
| `HANDOFF.md` | yes | Your handoff note (section 10). |

You may add more `*.test.js` files or small helper `.js` modules inside your
folder. Nothing outside it.

### The `calculate()` contract

```js
// raw = what the user typed/selected, keyed by input "name" from meta.json (strings)
calculate({ length: '10', width: '12', waste: '10' })
// success:
{ ok: true, results: { total: 132, area: 120 }, chart: [{ label: 'Area', value: 120 }, ...] }
// invalid input:
{ ok: false, errors: { length: 'Length must be greater than 0.' } }
```

- Every `results` key must match an `outputs[].name` in `meta.json`.
- Every `errors` key must match an `inputs[].name`; the message is shown under that field.
- `chart` is optional and only drawn when `chartStyle` isn't `"none"`.
- Use the helpers in `@tools/calculator-core` (import them, never copy or edit them):
  `validateAll`, `validateNumber`, `parseNumber`, `round`, `ceilTo`, `formatNumber`,
  `withWaste`, `cuFtToCuYd`, `inchesToFeet`, `feetAndInches`, `sqFtToSqYd`, and the
  constants `INCHES_PER_FOOT`, `CU_FT_PER_CU_YD`, `SQ_FT_PER_SQ_YD`.

### `meta.json` inputs and outputs

```json
"inputs": [
  { "name": "length", "label": "Length", "unit": "ft", "default": "10", "group": "Slab size", "help": "Measure the longest side." },
  { "name": "bagSize", "label": "Bag size", "type": "select", "default": "80",
    "options": [{ "value": "60", "label": "60 lb bag" }, { "value": "80", "label": "80 lb bag" }], "group": "Bags" }
],
"outputs": [
  { "name": "cubicYards", "label": "Concrete needed", "unit": "cu yd", "decimals": 2, "primary": true }
]
```

`name` is camelCase letters and numbers. Inputs with the same `group` share a
fieldset (a numbered step in the `stepper` layout). Input `type` is `number`
(default) or `select`.

#### Optional input settings (shared frame, Oct 21, 2026)

**`"advanced": true`** puts the input inside one collapsible **Advanced
settings** section (a native `<details>`) after the main groups. It's closed by
default, works without JavaScript, and opens by itself when one of its fields
has a non-default value or an error. Use it for secondary inputs: waste %,
coverage or density overrides, product presets, fastener counts. Inputs keep
their `group`; inside the section an `"Advanced: ..."` prefix is dropped from
the group label. Optional top-level `"advancedLabel"` renames the section.
Don't put an input most visitors must change in Advanced.

**`"showIf"`** shows the input only when another input matches, e.g.

```json
{ "name": "battR", "showIf": { "field": "product", "equals": "batts" }, ... }
{ "name": "diameter", "showIf": { "field": "shape", "in": ["circle", "ring"] }, ... }
{ "name": "x", "showIf": [{ "field": "a", "equals": "1" }, { "field": "b", "notEquals": "0" }], ... }
```

`equals`, `notEquals`, `in`, or an array (all must match). A hidden input is
hidden from screen readers too, and is **left out of the values passed to
`calculate()`**, so `logic.js` must validate and use only the fields for the
chosen mode/shape/product (a hidden field arrives as `undefined`). The typed
value comes back when the field is shown again. A group whose fields are all
hidden hides too. Without JavaScript every field shows, so `logic.js` must also
ignore fields that don't apply. Never hide or show fields from `ui.js`; use
`showIf`.

**Chart highlight.** In `calculate()`'s `chart` array, mark the row that
matches the visitor's own input or result with `highlight: true` and an optional
short `highlightLabel` (default "Yours"), e.g.
`{ label: '6 in', value: 34, highlight: true, highlightLabel: 'Your depth' }`.
The frame outlines it in `--tool-ink`, adds the text label, and names it in the
chart's accessible title (never color alone). Highlight at most one row, and
only when the chart has a real "yours" point (a comparison across sizes or
options, not a breakdown of one result).

**Tables in `page.md`** scroll inside themselves on phones automatically; don't
add `display: block` / `overflow-x` table rules in `tool.css`.

### Results card, labeled chart, and labeled diagram (shared frame, Nov 2026 redesign)

The Nov 2026 redesign PR changed the shared frame for every tool at once. That
PR was an explicit, one-time exception to the "never touch `packages/`" rule.
**Single-tool builders still never edit `packages/` or the site's `src/`:** you
inherit all of this from `meta.json` and `calculate()`.

**Layout.** `"layout"` defaults to `"split"`: inputs on the left; the results
card, diagram, and chart on the right from 48rem wide. On phones the results
follow the inputs, and a small sticky bar shows the headline number while the
form is on screen. Keep the main form short; put secondary inputs in Advanced.

**Results card** (all from `meta.json` `outputs`):

| Output field | Effect |
|---|---|
| `"primary": true` | The **first** primary output is the large headline number. Any further primaries become key-figure tiles under it (3 or fewer reads best). |
| `"group": "Buy"` | Non-primary outputs are grouped into a receipt-style breakdown, in the order groups first appear (default group "Details"). |
| `"unitGroup": "volume"` | Outputs sharing a `unitGroup` are **one row** showing the same quantity in two US units (cu yd and cu ft, sq ft and sq yd). The card gets a unit toggle; without JavaScript both show. List the members in the same unit order in every group (larger unit first). Optional `"unitGroupLabel"` names the row. Never add metric. |
| `"format": "yesno"` | Shows a 1/0 flag as Yes/No (drop "(1 = yes)" from the label). |
| `"format": "fraction"` | Shows inches to the nearest 1/16 in, e.g. `7 1/2`. |
| value `null` | A result that doesn't apply (an optional extra left blank) hides its row. |

Copy, Share (Web Share API, or copies a link that prefills the inputs from the
URL query, e.g. `?length=12&width=10`), Print, the estimates notice, and the
empty/invalid states are automatic.

**Chart.** Bar and line charts draw axis lines, ticks, gridlines, a value-axis
unit, a category-axis label, and the value on every bar/point. Set
`"chartUnit"` (e.g. `"bags"`) and `"chartXLabel"` (e.g. `"Slab thickness (in)"`)
in `meta.json`; if they depend on the inputs, `calculate()` may return
`chartUnit` / `chartXLabel` to override them. Donut charts print each value,
its share, and the total.

**Diagram.** Every tool should return a labeled drawing of what the visitor
entered: add a `diagram` object to `calculate()`'s success result. It is plain
data, used only for labels, never for math. The frame renders it at build time
with the `meta.json` defaults (so it's in the HTML without JavaScript) and
redraws it on every input, with `role="img"` and an `aria-label` that states
the dimensions. Optional `"diagramCaption"` in `meta.json` sets the caption.

| `type` | Fields (all optional except the sizes) |
|---|---|
| `box` | `length`, `width`, `depth`, `unit` ("ft"), `depthUnit` ("in"), `layers: [{ label, depth }]`, `pattern`, `caption` |
| `cylinder` | `diameter`, `height`, `unit` ("in"), `count` |
| `plan` | `length`, `width`, `unit`; or `shape: "circle" \| "ring"` with `diameter` (`innerDiameter` for a ring); or `areas: [{ label, length, width }]` for several rooms; `pattern` (`hatch`, `boards-h`, `boards-v`, `pavers`, `brick`, `block`, `turf`, `shingles`), `gridSpacing` (in), `joists` (in), `arrow`, `depthNote`, `caption` |
| `triangle` | `rise`, `run`, `slope`, `unit`, `angle`, `pitch` (x/12), `riseName` / `runName` / `slopeName` |
| `stairs` | `risers`, `riserHeight`, `treadDepth`, `totalRise`, `totalRun`, `stringerLength`, `topLabel` |
| `fence` | `length`, `height`, `posts`, `spacing`, `gates`, `unit` |
| `wall` | `length`, `height`, `gableRise`, `unit`, `pattern`, `windows`, `doors`, `moduleLabel`, `caption` |
| `room` | `length`, `width`, `height`, `unit`, `ceiling` (bool), `wallLabel`, `ceilingLabel` |
| `attic` | `pitch`, `intakeLabel`, `exhaustLabel`, `insulationDepth`, `insulationLabel`, `spanLabel`, `caption` |

Any dimension label can be replaced with a ready-made string, e.g.
`lengthLabel: "12 ft 6 in"`. Drawings are schematic: proportions follow the
inputs within limits so thin or huge values stay readable. Example:

```js
diagram: { type: 'box', name: 'Slab', length: 10, width: 10, depth: 4, unit: 'ft', depthUnit: 'in' },
```

**Homepage card.** `"cardBlurb"` is the 5 to 12 word benefit shown on homepage
and related-tool cards (falls back to `benefit`). `"category"` must match a
category in `src/categories.mjs` (ask for a new category in `HANDOFF.md`
instead of inventing one).

## 3. Naming rules

- Tool slug = folder name = URL: kebab-case, lowercase letters, numbers, single
  hyphens, max 60 characters. Example: `concrete-slab` -> `/concrete-slab/`.
- Describe the tool, not a keyword stuffing exercise: `paver-base`, not
  `best-free-paver-base-gravel-calculator-online`.
- Reserved (can't be used): `about`, `contact`, `privacy`, `terms`, `disclaimer`,
  `how-we-build`, `404`, `index`, `robots`, `sitemap`, `ads`, `favicon`, `page`,
  `tools`, `assets`, and anything starting with `_`.
- Use the slug you were given. If none was given, propose one in `HANDOFF.md`.

## 4. Start a tool with the scaffold

From the repo root:

```sh
npm ci
npm run new-tool -- --site home-project-calcs --tool <tool-slug>
# --slug works as an alias for --tool
```

This copies `tools/_template/` to `tools/<tool-slug>/` and generates the thin page
file `src/pages/<tool-slug>.astro`. That page file is needed for your local build,
but it is **not** part of your handoff; don't edit it.

A freshly scaffolded tool **fails `npm test` on purpose** until you replace the
template example in `logic.js` (delete the `TEMPLATE_EXAMPLE` line) and every
`TODO` in `meta.json` and `page.md`.

## 5. What you may and may never change

**You may change:** files inside `sites/home-project-calcs/tools/<tool-slug>/` only.

**You must NEVER touch:**
- `packages/` (layout, calculator-core, seo, ad-slot, consent): never edit, copy, or fork
- the site's `src/` folder: layouts, pages (including the generated `src/pages/<tool-slug>.astro`), styles, `site.config.mjs`, `content.config.mjs`, content pages
- `tools/_template/` or any other tool's folder
- root `package.json`, `package-lock.json`, the site's `package.json`
- `.github/`, `scripts/`, `docs/`
- `wrangler.jsonc`, `astro.config.mjs`, `vitest.config.mjs`
- `robots.txt` (generated), `public/ads.txt`, anything about ads, ad slots, consent, or AdSense
- secrets of any kind: no `.env` files, API keys, tokens, or passwords anywhere

**Also never:**
- install packages (`npm install <pkg>`). If you need a dependency, list it under
  "Dependency requests" in `HANDOFF.md` with the reason, and build without it.
- add analytics, trackers, ad code, external scripts, web fonts, CDN links, iframes,
  `fetch`/XHR calls, cookies, or `localStorage`. Calculators run fully in the
  browser and send nothing anywhere.
- deploy, run `wrangler login`/`wrangler deploy`, push to any branch (especially
  `main`), or open pull requests. The Web Dev bot does all of that after review.

If the shared frame can't do something you need, don't work around it. Describe
the need under "Open questions" in `HANDOFF.md`; it becomes a separate infra change.

**Calculator data and assumptions: decide, don't ask (standing rule, Oct 7, 2026).**
For any question about calculator data or assumptions (defaults, formulas, code
editions, rounding, waste factors), use the industry standard or, if there isn't
one, the most sensible option. Don't ask the site owner. Record each choice and
its source (with a link) under "Decisions made" in `HANDOFF.md`; the Web Dev bot
copies them into the PR body. Product, UX, and scope questions still go to
Matthew under "Open questions".

## 6. Page anatomy (required)

The shared frame renders, in order: breadcrumbs, category, H1, intro, hero, the
calculator (inputs beside the results card, diagram, and chart), "Last updated"
with the byline, ad space, **your `page.md`**, Sources (from `meta.json`),
related tools, ad space. Schema (WebApplication + BreadcrumbList, plus FAQPage
built from your FAQ questions), the canonical URL, and the footer legal links
are automatic.

**Every `page.md` H2 becomes a collapsible section** (native `<details>`,
closed by default; "How to use" stays open when it has 5 steps or fewer). Each
`###` FAQ question becomes its own collapsible item. Nothing is removed from the
HTML, so the copy still counts for search, but keep it tight: the intro is one or
two sentences, and the calculator, results card, and diagram already explain a lot.
Use the exact H2 names below so the frame recognizes each section.

**Title pattern** (built automatically from `meta.json`):
`[Tool name] - [main benefit] | Home & Yard Calcs`
- `title` = tool name, also the H1, e.g. `Concrete Slab Calculator`
- `benefit` = main benefit, e.g. `Cubic Yards and Bags for Any Slab`
- Aim for title + benefit under about 45 characters so the full title stays near 70.
- Optional `seoTitle` = Content & SEO's approved title text before ` | Home & Yard Calcs`; it replaces `[title] - [benefit]` in `<title>`/`og:title` only (the H1 still uses `title`). Keep the full title at 60 characters or fewer.
- `metaDescription`: what it calculates, in US units, plus one differentiator (140-160 characters).

**`page.md` H2 sections, in this order:**
1. `## What it calculates and who it's for`
2. `## How to use` (steps matching the form)
3. `## The formula` (every variable explained, with units)
4. `## Worked example` (real numbers, step by step, recalculated by hand; must match what the tool outputs)
5. `## How to read your results` (rounding up to whole bags/boards/sheets, buying tips)
6. `## Assumptions and limits` (what it doesn't cover; tell readers to confirm with their supplier and follow product instructions and local codes)
7. `## FAQ` (real questions as `###` headings, short answers)
8. One **unique addition** as its own H2: a comparison table, scenario toggle, printable summary, or real-world tip (or the chart, described in `uniqueAddition`)

Do **not** write an H1, a Sources section, or a "last updated" line in `page.md`;
they come from `meta.json`.

**Units:** US customary only: feet, inches, square feet, square yards, cubic feet,
cubic yards, pounds, and US bag sizes (e.g. 40, 50, 60, 80 lb). Show units on
every input and result.

**Content rules:**
- Written for this tool only. Never reuse resource, guide, or source text from another tool.
- Every rate, coverage figure, or bag yield comes from a real, reachable source listed in `meta.json` `sources` with an `accessed` date (YYYY-MM-DD). Never invent a source or a number.
- Default waste allowances are stated and explained.
- No click-request wording about ads (e.g. "click the ads", "support us by clicking").
- No claims of contractor experience, licenses, or credentials for the site or its author.
- No legal text (privacy, terms, disclaimers beyond the assumptions-and-limits note).
- `lastUpdated` = the date you finished the content (YYYY-MM-DD).

## 7. Give the tool its own look

Every tool shares one frame but shouldn't look stamped out. Vary these, from your folder only:

| Variety | How |
|---|---|
| Accent / theme | Override tokens in `tool.css` inside `[data-tool="<tool-slug>"] { ... }`: `--tool-accent`, `--tool-accent-ink` (text on accent), `--tool-surface`, `--tool-ink`, `--tool-border`, `--tool-radius`, `--tool-font-display`, `--chart-palette-1` to `--chart-palette-4` |
| Layout | `meta.json` `"layout"`: `"split"` (default: inputs and results side by side on wide screens), `"stepper"` (the same, with each input group as a numbered step), or `"stacked"` (one column), plus small touches in `tool.css` |
| Illustration | `assets/hero.svg` (or png/jpg/webp/avif), under 100 KB. Decorative = leave `"heroAlt": ""`; meaningful = describe it in `heroAlt` |
| Chart | `meta.json` `"chartStyle"`: `"bar"`, `"line"`, `"donut"`, or `"none"`, fed by `chart` from `calculate()` and colored by your `--chart-palette-*` |
| Results headline | You may restyle `.calc-primary` (and its `__label`, `__value`, `__unit`) inside your scope, e.g. a solid accent panel. Keep AA contrast. Diagrams follow `--tool-accent` and `--tool-ink` automatically. |

Rules for `tool.css`:
- Every selector starts with `[data-tool="<tool-slug>"]`. CI fails anything else.
- Never target `.ad-slot`, `[data-ad-slot]`, `--ad-slot-height`, consent, `header`, `footer`, `.site-header`, `.site-footer`, `html`, `body`, or `:root`.
- WCAG AA contrast: 4.5:1 for normal text, 3:1 for large text and UI parts (check `--tool-accent-ink` on `--tool-accent`, and `--tool-ink` on `--tool-surface`).
- System font stacks only (no web fonts, no `@import`, no external URLs).
- Pick a look that differs from existing tools on the site.

## 8. Testing requirements

In `logic.test.js` (Vitest):
- **At least 3 known-answer cases**, each with its reference in the test name or a
  comment: a named trusted calculator (with URL) or hand math written out.
- **Edge cases**: zero, negative, very large, empty, non-numeric, and the
  boundary values of every input (just inside and just outside each limit).
- Assert both `ok: true` results and `ok: false` errors keyed to the right input.
- Keep the **scaffold guard** block at the bottom unchanged.
- The worked example in `page.md` must also be a test case.
- Test that `calculate()` returns your `diagram` (a shared test also renders every
  tool's diagram at its defaults and fails on `NaN` or a missing label).
- If `page.md` has a sourced table, add a test that reads the table and checks
  each row against `calculate()`.

## 9. Commands (run from the repo root)

```sh
npm ci                              # install exact versions (never npm install <pkg>)
npm test                            # all unit tests must pass
npm run build                       # must finish with "Complete!"
npm run check                       # repo checks; warnings about the placeholder domain/ads.txt are expected
npm run dev:home-project-calcs      # optional: preview at http://localhost:4321/<tool-slug>/
```

Check your page on a phone-width window: the calculator should be visible
without scrolling past the intro.

## 10. Handoff format

Deliver **one zip** containing only your tool folder, with its repo path kept:

```sh
# from the repo root
zip -r <tool-slug>.zip sites/home-project-calcs/tools/<tool-slug> -x '*/node_modules/*' '*/.DS_Store'
```

Do not include `src/pages/<tool-slug>.astro`, `package.json`, the lockfile, or anything
else. The bot regenerates the page file with
`npm run new-tool -- --site home-project-calcs --tool <tool-slug> --page-only`.

`HANDOFF.md` inside the folder must list:
1. **What was built**: slug, tool name, one-sentence description, layout/chart/accent chosen
2. **Sources used**: title, URL, accessed date, and what each one supports
3. **Test and build results**: the summary lines from `npm ci`, `npm test`, `npm run build`, and the known-answer references
4. **Decisions made (choice, source)**: every data/assumption choice (defaults, formulas, code editions, rounding, waste factors) with its source link (see the rule in section 5)
5. **Open questions**: product, UX, or scope questions for Matthew, and anything the frame couldn't do
6. **Dependency requests**: package + reason, or "none"

## 11. What happens next (not your job)

The Web Dev bot unzips the folder, regenerates the page file, runs the tests and
build, and opens one pull request for the tool, copying "Decisions made" into the
PR body. The site owner reviews it on a preview link and approves it. Nobody else merges, pushes to `main`, or deploys.
